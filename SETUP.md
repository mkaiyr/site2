# Setup guide — Concord / Kablan

Полный пошаговый гайд: от пустого аккаунта Supabase до опубликованного на
GitHub Pages сайта. Код уже написан и ждёт только этих настроек — ничего
руками в JS/HTML менять не нужно, кроме одного файла с двумя строчками
(шаг 6).

---

## 1. Создать Supabase-проект

1. Зайдите на https://supabase.com/dashboard → **New project**.
2. Выберите организацию (или создайте), задайте:
   - **Name** — например `concord-kablan`;
   - **Database Password** — сгенерируйте и сохраните где-нибудь (это пароль
     от самого Postgres, не имеет отношения к паролям администраторов сайта);
   - **Region** — ближайший к вам.
3. Нажмите **Create new project** и подождите 1–2 минуты, пока он поднимется.

---

## 2. Выполнить SQL-схему

1. В боковом меню откройте **SQL Editor → New query**.
2. Откройте файл `schema.sql` из этого проекта, скопируйте **всё содержимое**.
3. Вставьте в редактор и нажмите **Run**.

Это создаст одним запуском:
- `cafeterias` — строки `concord` / `kablan`;
- `menu_items` — сами блюда (столовая, дата, категория, название, цена, вес,
  порядок сортировки, флаги «блюдо дня» / «в комплексный обед» / «скрыто»);
- `menu_day_status` — можно ли показывать день целиком, и время обновления;
- `admins` — список пользователей с правом редактировать меню;
- политики Row Level Security на все таблицы (см. ниже, шаг 3);
- демонстрационное меню на сегодня для обеих столовых.

Файл можно перезапускать сколько угодно раз — все операции написаны так,
что не создают дублей.

---

## 3. Row Level Security — что уже настроено

RLS включён на все таблицы прямо в `schema.sql`, руками ничего дополнительно
делать не нужно. Логика:

| Таблица | Кто может читать | Кто может писать |
|---|---|---|
| `cafeterias` | все | никто с фронтенда |
| `menu_items` | все — но только строки с `hidden = false`; админ видит всё | только те, чей `user_id` есть в `admins` |
| `menu_day_status` | так же | только админы |
| `admins` | только сам пользователь свою запись | никто с фронтенда |

Проверка «админ или нет» сделана функцией `is_admin()` с `security definer`,
чтобы не было циклических зависимостей политик. Обычный посетитель сайта
физически не может ни добавить, ни изменить, ни удалить блюдо — даже если
напрямую дёрнет Supabase REST API, минуя ваш сайт.

---

## 4. Включить и настроить Auth

1. **Authentication → Providers → Email**.
2. Отключите **Allow new users to sign up** — чтобы никто посторонний не
   мог сам себе завести аккаунт. Учётные записи администраторов создаёте
   только вы, вручную (следующий шаг).
3. Остальные настройки (подтверждение email и т.п.) можно оставить по
   умолчанию — на схему доступа они не влияют, доступ разграничен через RLS.

---

## 5. Создать 5 администраторов

1. **Authentication → Users → Add user**.
2. Для каждого администратора:
   - укажите email и пароль;
   - включите **Auto Confirm User**, чтобы не подтверждать почту вручную.
3. После создания в списке **Users** скопируйте **UUID** этого пользователя.
4. В **SQL Editor** выполните для каждого администратора отдельно:

   ```sql
   insert into admins (user_id, full_name)
   values ('ВСТАВЬТЕ-UUID-СЮДА', 'Имя Фамилия');
   ```

Повторите для всех пяти. Без строки в `admins` человек может ввести верный
пароль, но панель тут же покажет «У вас нет прав администратора» и разлогинит
его — доступ на запись в самой базе тоже будет отклонён (это RLS, а не
проверка в интерфейсе, которую можно обойти).

Добавить шестого администратора позже — ровно та же процедура, изменений в
коде не требует.

---

## 6. Взять Supabase URL и Anon key, вставить в проект

1. **Project Settings → API**.
2. Скопируйте:
   - **Project URL** — выглядит как `https://xxxxxxxx.supabase.co`;
   - **Project API keys → anon public** — длинная строка.
3. Откройте файл `supabase-config.js` и замените:

   ```js
   const SUPABASE_URL = "https://YOUR-PROJECT-REF.supabase.co";
   const SUPABASE_ANON_KEY = "YOUR-ANON-PUBLIC-KEY";
   ```

   на реальные значения из пункта 2.

**Важно:** это именно `anon public` ключ — его и положено видеть в коде
страницы, доступ к данным ограничивает не секретность ключа, а RLS-политики
из шага 3. **Никогда не используйте здесь `service_role` ключ** — у него нет
никаких ограничений доступа, и во фронтенде ему не место.

---

## 7. (Рекомендуется) включить Realtime

Чтобы изменения администратора появлялись у всех посетителей мгновенно, без
перезагрузки страницы:

1. **Database → Replication**.
2. Включите репликацию для таблиц `menu_items` и `menu_day_status`.

Без этого шага сайт тоже полностью рабочий — просто новое меню подтянется
при следующем открытии/обновлении страницы, а не мгновенно.

---

## 8. Запустить и проверить локально

Откройте `index.html` прямо в браузере (двойным кликом или через
`npx serve .` / любой локальный статический сервер — Supabase обращается
к вашему проекту по сети, локальный сервер файлов не нужен, но некоторые
браузеры аккуратнее ведут себя с `file://`, если через сервер).

Проверьте по списку:

- [ ] Открывается **Concord** по умолчанию, с сегодняшним демо-меню.
- [ ] Переключение на **Kablan** — меняется и заголовок, и список блюд.
- [ ] На публичной странице нет кнопки/ссылки на админку.
- [ ] Откройте `admin.html` — экран входа, без пароля по умолчанию.
- [ ] Войдите одним из созданных в шаге 5 админов.
- [ ] Попробуйте войти под email, для которого **не** выполнен шаг 5 —
      должно быть отказано с сообщением «нет прав администратора».
- [ ] В админке выберите столовую **Kablan**, измените цену блюда,
      «Сохранить меню» — на публичной странице (при выбранной Kablan)
      цена обновилась.
- [ ] Проверьте, что то же самое изменение **не** появилось у Concord.
- [ ] Сделайте день скрытым («Скрыть меню на этот день») — на сайте
      должно показаться «Меню временно обновляется».
- [ ] Удалите все блюда на какой-то будущей дате (или просто откройте
      админку на дату, где ничего нет) — на сайте для сегодняшнего дня
      это не аффектит; чтобы проверить пустой экран, временно очистите
      сегодняшнее меню одной из столовых — должно показаться «Меню на
      сегодня пока не опубликовано», а не пустая страница.
- [ ] Стрелки ↑/↓ у блюда и у категории меняют их порядок — после
      «Сохранить меню» порядок сохраняется и виден на сайте.
- [ ] Откройте DevTools → Console на обеих страницах — ошибок быть не
      должно (кроме, возможно, предупреждения о шрифтах при офлайн-работе
      без интернета — это нормально).
- [ ] Проверьте на телефоне (или через DevTools → responsive mode) —
      320–480px, планшет, десктоп: без горизонтального скролла, кнопки не
      наезжают друг на друга.

---

## 9. Опубликовать через GitHub Pages

1. Создайте новый репозиторий на GitHub (публичный или приватный — Pages
   работают для обоих, для приватного нужен план с поддержкой Pages).
2. Загрузите в него все файлы одним набором, в корень репозитория:
   ```
   index.html
   admin.html
   style.css
   script.js
   admin.js
   supabase-config.js   ← уже с вашими реальными URL и anon key
   schema.sql            (можно не публиковать — не нужен рантайму сайта)
   ```
   Через веб-интерфейс GitHub: **Add file → Upload files** — или обычным
   `git add . && git commit -m "init" && git push`.
3. В репозитории: **Settings → Pages**.
4. **Source** → **Deploy from a branch**.
5. **Branch** → выберите `main` (или `master`), папка `/ (root)` → **Save**.
6. Через минуту-две GitHub покажет адрес вида:
   ```
   https://ВАШ-ЛОГИН.github.io/НАЗВАНИЕ-РЕПОЗИТОРИЯ/
   ```
   Это и есть публичный сайт. Админка находится по адресу:
   ```
   https://ВАШ-ЛОГИН.github.io/НАЗВАНИЕ-РЕПОЗИТОРИЯ/admin.html
   ```
7. Проверьте список из шага 8 ещё раз уже на реальном адресе.

**Про CORS:** Supabase по умолчанию принимает запросы с любого домена для
`anon`-ключа, поэтому дополнительно ничего настраивать не нужно — сайт с
GitHub Pages будет обращаться к вашему проекту Supabase без проблем.

**Обновление сайта в будущем:** просто закоммитьте изменённые файлы в тот
же репозиторий — GitHub Pages передеплоит их автоматически за 1–2 минуты.
Изменения в меню (через `admin.html`) отдельного деплоя не требуют вообще —
они идут напрямую в базу данных.

## Что уже устроено в коде — коротко

- Никаких данных в `localStorage` — всё меню в Supabase. `localStorage`
  используется только для одной мелочи: запомнить, какую столовую вы
  смотрели последней в этом браузере (это не данные меню, а личная
  настройка отображения).
- Concord и Kablan физически разделены полем `cafeteria_id` — блюда одной
  столовой не могут попасть в выдачу другой ни при каких обстоятельствах.
- Публично показывается только сегодняшнее меню; прошлые дни остаются в
  базе для истории и для кнопки «Скопировать предыдущий день», но обычным
  посетителям не показываются.
- Пустой или скрытый день — аккуратное сообщение вместо пустого экрана.
- Реальная авторизация через Supabase Auth, без единого пароля в коде.
- Права на запись проверяются в самой базе данных (RLS), а не только в
  интерфейсе — это защита, которую нельзя обойти с фронтенда.
- Добавление, редактирование, удаление и ручная сортировка (стрелки ↑/↓)
  блюд и категорий — прямо в админке, изменения видны всем сразу.
